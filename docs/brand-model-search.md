# Поиск по бренду и сохранение модели

Проверено 31 октября 2026 года на основной заполненной PostgreSQL, HTTP API и
установленном Edge. Используются существующие unified grid, проектные запросы,
ревизии и фильтры. Миграций и изменений импортера нет.

## Первопричины

Фактический путь: сообщение → `ProjectQueryService.request` → `grid_plan` →
Query Understanding / существующий role parser → `ResearchIntent.branches` →
SQL → проверка назначения → модель → дополнительные фильтры → пагинация → HUD.
В unified grid решения принимает `ProjectQueryService`; старый
`ConversationQueryRouter` не находится на этом execution path. Второй router
или поисковый движок не добавлялись.

Для `Ручка шариковая Tippo` Query Understanding сохранял уточнение. Первая потеря
смысла происходила при построении `ProductBranch`: оставались категория `pen`,
цвет, материал, цена и количество, но отсутствовало обязательное условие модели.
SQL и purpose gate затем принимали все пишущие ручки. VORTEX попадал законно
относительно этого неполного плана и сортировался раньше по offer ID. Изменение
ранжирования не устранило бы лишние модели.

`Tippo` — подтверждённая часть названия семейства, а не бренд. В live-каталоге
нет заполненных отдельных `metadata.model` / `model_name`; используется
`metadata.parent_name`. У шести Tippo бренд `Без бренда`. У двух VORTEX — `B1`.
Melango — другое подтверждённое семейство: четыре варианта, бренд Molti.

Бренды ранее извлекались отдельным regex после разбора категории. Одиночный
`Molti` маршрутизировался как фильтр прежнего поиска. Неизвестный явно заданный
бренд мог вообще не изменить предыдущую выдачу. Идентичность бренда в текстовом
поиске и HUD также не имела общего механизма Unicode-нормализации.

## Исправления

- Реестр из актуальной DISTINCT-проекции структурированного `SupplierOffer.brand`,
  уже сохранённого VTO-адаптером с наследованием родителя/варианта. Нет enum,
  ручного перечня брендов, восстановления старых поставщиков или нового импорта.
- NFKC, регистр и повторные пробелы нормализуются; пунктуация сохраняется.
  Сначала сопоставляется полное многословное название. SQL использует реальные
  исходные написания из того же реестра: результат не зависит от PostgreSQL
  C-locale и его ограничения при приведении кириллицы к нижнему регистру.
- Однозначный отдельный бренд создаёт NEW_SEARCH по всем категориям. Бренд,
  модель, исключения и локальная область сохраняются в intent. Категория AND
  бренд AND остальные ограничения остаются обязательными.
- Модель сопоставляется последовательностью полных Unicode-токенов с отдельным
  полем модели либо основным названием семейства. `Tippo` не равно `Tippomatic`;
  `Deep Space` не равно `Deep Spacex`. Упоминания в совместимости/комплектности
  не заменяют основное назначение или структурированного владельца бренда.
- Неизвестное явное условие даёт пустую выдачу с объяснением. Модель не заменяется
  общей категорией. Похожие товары автоматически не подмешиваются.
- Конфликт бренд/модель требует уточнения. Категория позволяет разрешить конфликт
  B1: бренд ручек и часть названия лампы Rombica. Слово `Pen` внутри полного
  бренда `Lecce Pen` не является самостоятельной неоднозначной категорией.
- Глобальный бренд применяется ко всем веткам; локальные ветки объединяются OR,
  несколько брендов одной категории также OR. Нулевая ветка не обнуляет остальные.
- «Оставь только» сохраняется в ResultViewState; замена бренда снимает прежний
  положительный бренд; «бренд не важен» снимает исходные и дополнительные
  брендовые условия через ревизию. Новый поиск не наследует фильтры.
- HUD показывает исходные и дополнительные бренды/модели, включая область.
  Исходный бренд отмечен в dropdown и не снимается сбросом дополнительных
  фильтров. Для его снятия доступна явная команда в том же чате.

При проверках исправлены две обнаруженные регрессии: `300шт` перестало быть
моделью; неизвестный одиночный термин передаётся существующему Query
Understanding, чтобы сохранить исправление `корондаш → карандаш` и открытые
категории вроде `фляжки`. Материалы исключаются из модели существующим material
resolver. Неизвестное название не исправляется произвольно до популярного бренда.

Изменены `domain/research.py`, новые domain/application `catalog_identity.py`,
`application/product_grid.py`, `application/project_queries.py`, типы research,
существующие компоненты фильтров и workspace. Постоянные проверки:
`test_brand_model_search.py`, `product-grid.test.cjs`,
`scripts/check_brand_search.py`, `scripts/check_brand_browser.py`.

## HTTP, UI и состояние

В изолированных проектах прошли последовательные команды: общий поиск ручек и
рюкзаков → только Molti (4) → другой бренд B1 (7) → Undo (4) → бренд не важен
(243) → без Molti (239) → ограничение отдельной ветки → новый поиск бутылок
(134, без наследования) → ручки → модель Tippo (6). Сохранённые intent сверены
с PostgreSQL, а view — с повторным GET. Исходный Molti сохранился после reset;
«бренд не важен» расширил его поиск рюкзаков с 4 до 86. История восстановила
Melango. Выбранный `vto:1823109` сохранился независимо от поиска и фильтров.

Два пользователя одновременно запросили Tippo и Molti в разных проектах.
Получены независимые правильные ID-наборы; чтение чужих history/research/collection
вернуло 404. Нет новых 500/503 в завершённой HTTP-цепочке. Старые ответы защищены
существующими generation/version/cursor guards; проверяются постоянными тестами.

В установленном Edge прошли 11 DOM-проверок: Tippo и его плашка, самостоятельный
Molti и отмеченный исходный checkbox, reset, F5, фактический выбор B1 в HUD,
Melango, неизвестная модель, история, первая и все страницы ROLY, mobile без
горизонтального overflow. Desktop 1440×1000 и mobile 390×844 просмотрены как
скриншоты. Native keyboard input использовался для отправки сообщений.
Первый browser harness слишком рано отправил запрос до загрузки проекта и
ожидал включения пустой кнопки composer; harness исправлен и весь сценарий
повторён. Этот ранний прогон не считается PASS. Созданный им дополнительный
проект принадлежит тестовому пользователю и записан для точной очистки.

## Производительность

Бренд фильтруется SQL до purpose/model проверки. Модель проверяется по полной
скалярной проекции, до пагинации. Тысячи Product DTO не создаются; гидратируются
только текущая страница и проектный выбор. Скрытого top-N нет.

Реестр брендов и family projection читаются заново из PostgreSQL; новый бренд
виден сразу. Bounded model cache включает сами модели, родительское название,
заголовок и структурированное поле. Ключ пагинации включает весь intent,
дополнительные фильтры и их область. Обычные известные бренды/модели не вызывают
Qwen, VTO HTTP или импорт; supplier_http остаётся 0, QU фиксирует llm_used=false.

В исходном baseline семь запросов заняли 0.080–0.489 s. После изменения первый
Tippo после рестарта занял 2.085 s; следующие запросы первоначальной цепочки —
0.465–0.705 s. Дополнительная скалярная проверка всего каталога увеличивает
задержку; это оставшееся ограничение. Измерения выполнялись одновременно с
backend suite, не являются изолированным benchmark или нагрузочным p95.
Последняя расширенная серия: 25 различных измеренных команд, p50 0.608 s,
p95 0.795 s, диапазон 0.264–0.879 s; это только smoke sample.

поле модели проверены fixtures; наличие такого live-товара не выдумывается.

## Сохранность и воспроизведение

До и после: 4495 SupplierOffer; одинаковый коммерческий offer/observation
fingerprint `276337c6419e9c7c71382497655c5ec1`. Все **8** существовавших до
проверки presentation drafts сохранили собственные fingerprints. База, цены,
остатки, availability policy LAST_KNOWN_STOCK_ALLOWED, фото, PDF renderer,
snapshots, реальные пользователи и их подборки не менялись кодом задачи.
Jobs/checkpoints не сбрасывались. Фоновый worker использует прежнюю инфраструктуру.

HTTP-проверки: `python scripts/check_brand_search.py prepare`, затем `baseline`
на старой версии или `run`/`extended` на новой; `cleanup` удаляет только
зарегистрированные disposable IDs. Для DOM-проверки используется существующий
Edge с отдельным профилем и портом 9226, затем
`python scripts/check_brand_browser.py`. Ledger содержит cookies, не публикуется
и удаляется после проверки. Постоянные тесты и эти воспроизводимые scripts
сохраняются. Временная очистка и финальные health checks фиксируются ниже.

Очистка завершена: SQL подтвердил **0** оставшихся disposable users/projects,
4495 offer с прежним fingerprint и все 8 прежних drafts без изменения.
Удалены ledger/cookies, debug screenshots, временные test/profiling logs и
отдельный профиль Edge; debugging browser закрыт. Сохранены только постоянные
тесты/scripts и активные service logs. API, frontend и frontend API health proxy
после очистки вернули **HTTP 200**. PostgreSQL, Ollama, API и frontend работают.
