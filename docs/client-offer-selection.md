# Выбор клиента и уведомления — 11 ноября 2026

**PARTIAL для внешнего выпуска.** Реализованы и проверены сохранение клиентских
отметок, менеджерский раздел и постоянные уведомления. Основной API и локальный
production frontend обновлены. На `https://souvenir-studio-three.vercel.app`
работают новые API и SSE через восстановленный пользователем ngrok, но размещённый
frontend остаётся прежним: новых галочек там пока нет. Вход и deployment в Vercel
не выполнялись. Локальная проверка интерфейса не называется production UI PASS.

## Пользовательский путь

Гость открывает действующую ссылку, нажимает «Выбрать», видит «Выбрано: N» и
состояние сохранения. Это число позиций, а не тираж и не общая стоимость.
Повторное нажатие снимает отметку. При ошибке намерение сохраняется с кнопкой
повтора; неподтверждённая отметка явно обозначена. Возврат фокуса не скрывает
ошибку несохранённой операции. Цена, тираж, SKU и состав остаются недоступными
для гостевого редактирования.

В редакторе появился отдельный раздел «Выбор клиента»: посетитель, фотография,
название, SKU, время, исходные цена/тираж и предупреждение о смене условий или
удалённой позиции. В «Предложениях» отдельно указаны посетители, уникальные позиции
и число отметок. Колокольчик работает также вне research и редактора.
Уведомления сгруппированы по посетителю и документу; последнее снятие обновляет
группу до нуля. Доставка не означает прочтение. Переход к другому документу из
уведомления учитывает несохранённые правки.

Просмотр страницы, фотографий, клиентский preview редактора и скачивания сами
по себе не создают интерес. Галочки не попадают в печатный документ или PDF/XLSX.
Экспорты до/после клиентских операций совпали по SHA-256.

## Хранение и границы доступа

Сохранён прежний путь `Project → Document → PublishedRevision → Share` и правило
одного основного редактора на проект. Используется существующий UUID строки
предложения; порядковый номер, название и ID родительской модели не заменяют его.

Совместимая миграция `0028_client_selections` добавляет семь таблиц:

| Таблица | Содержание |
|---|---|
| offer_visitor_budgets | Общие лимиты документа и поколения ссылки |
| offer_visitors | Отдельная браузерная сессия, версия, срок и номер посетителя |
| offer_client_selections | Текущая отметка строки и увиденная опубликованная ревизия |
| offer_client_mutations | Квитанции идемпотентных операций |
| manager_event_cursors | Сериализуемая последовательность владельца |
| manager_events | Долговечный журнал событий для доставки и истории |
| manager_notifications | Одна обновляемая группа на посетителя; прочитанная последовательность |

ProjectCollection, DocumentRevision и коммерческие значения не используются как
хранилище интереса. Уникальность отметки — `(visitor_id,item_id)`, квитанции —
`(visitor_id,mutation_id)`. Сохраняется именно ревизия выбора: новая цена не получает
молчаливого подтверждения старой галочкой. Удалённая строка остаётся в истории,
не переносится на новый товар с тем же индексом массива.

GET состояния не создаёт посетителя. При первом действии выдаётся случайная
HttpOnly/Secure/SameSite=Lax cookie, ограниченная endpoint выбора конкретной
ссылки. БД хранит SHA-256 секрета. Cookie и CSRF не записываются в localStorage.
IP и fingerprint не определяют личность. «Посетитель N» — браузерная сессия,
а не установленная личность человека.

Поколение привязано к хешу действующего ключа ссылки. Ротация создаёт новый scope;
старый секрет не подходит. История прежнего поколения различима у менеджера.
Истечение, отзыв, удаление, текущая публикация и принадлежность строки проверяются
при каждой записи. Срок дополнительно проверяется перед commit: ожидание
блокировки не даёт права записать отметку после истечения. Выбор срок не продлевает.

Запись требует разрешённого Origin, JSON, отдельного заголовка действия и CSRF,
связанного с собственной cookie. UUID/version проходят строгую schema validation;
лишние поля, manager_id/visitor_id, чужие строки и коммерческие правки запрещены.
Сохранён существующий ограничитель размера HTTP-тела и публичных запросов.
Публичное состояние содержит только собственные ID строк/ревизий и служебные
поля своего сохранения, без других посетителей и складских данных.

Начальные конфигурируемые лимиты: 1000 сессий на поколение, 30 новых сессий/мин,
300 операций/мин на предложение, 90/мин и 2000 квитанций на посетителя,
100 000 квитанций на поколение. Создание новых cookie не обходит общий бюджет.
Достигнутый лимит не удаляет уже сохранённый выбор.

## Запись, порядок commit и SSE

Клиент отправляет желаемый `selected`, UUID операции, UUID публикации и текущую
версию сессии. Повтор квитанции и установка уже действующего значения не создают
новое логическое событие. Конфликт версии требует повторного чтения и применения
актуального намерения конкретной строки, без replace старого массива.

В одной короткой транзакции фиксируются отметка, версия, квитанция, событие и
группа уведомления. Гостевой порядок блокировок:
`Document → Share → Visitor → owner cursor → notification`.
Строка cursor блокируется до commit; другой процесс не может зафиксировать больший
номер раньше меньшего незавершённого события. Откат не оставляет дырку в счётчике.

Существующий research SSE имеет другой срок жизни и область авторизации. Для
аккаунта добавлен `/api/notifications/events`, использующий прежние middleware,
auth и Admission, а источником доставки служит PostgreSQL. Память процесса не
является очередью. Межпроцессная доставка проверена настоящими HTTP/SSE.

Подписка одна на авторизованное приложение во вкладке, без потоков на товар.
Сервер читает журнал короткими запросами примерно раз в 0,6 s; транзакция и
соединение не удерживаются между чтениями. Короткие DB-чтения защищены от
прерывания возврата соединения при ASGI disconnect. Поток живёт 25 s,
heartbeat — 10 s; затем штатное переподключение. `Last-Event-ID`/cursor поддерживают
replay; потерянный диапазон или невозможный cursor вызывают полную синхронизацию.
Передаются номера событий, без публичных ключей и клиентских секретов.

Есть ограничение 4 потока на пользователя / 16 на процесс, reconnect с backoff
1–30 s и один fallback-опрос раз в 15 s только для видимой онлайн-вкладки.
UI различает реальное время, задержанный опрос и отсутствие сети. Logout закрывает
подписку и очищает проекцию. Прочтение подтверждает конкретную увиденную
последовательность; более поздняя отметка остаётся непрочитанной.

Первое создание браузерной сессии согласуется через Web Locks с повторным GET
после получения блокировки; вкладки затем используют BroadcastChannel и версии.
Если BroadcastChannel отсутствует, используется только несекретный storage-сигнал.
Браузер без Web Locks получает объяснение о необходимости обновления при первом
сохранении, вместо небезопасной гонки создания двух сессий.

## Два обнаруженных дефекта и исправления

**SSE gzip buffering — исправлено.** Локальный Next production proxy сжимал
малые события и задерживал их в буфере. Реальный DOM показывал 3,6–12,7 s;
HTTP-проба с `Accept-Encoding: identity` получала событие немедленно, стандартная
gzip-проба задерживалась. Для потока установлен `Cache-Control: no-transform`,
сохранённый внешним middleware. Общая компрессия сайта не отключалась.

**Read/choice deadlock — исправлено.** При настоящей одновременной записи и
прочтении PostgreSQL вернул 40P01. `notification.read` брал owner cursor, затем
неявный FK `KEY SHARE` документа, который держала гостевая запись, ожидающая cursor.
Это событие относится к аккаунту и теперь имеет `document_id=NULL`; лишняя
FK-блокировка устранена. Новая отметка и read ack сохраняют версионирование.
Пять повторов реальной HTTPS/PG гонки прошли после исправления; сохранён opt-in
PostgreSQL-тест, поскольку SQLite такую FK-блокировку не воспроизводит.

Промежуточные ошибки acceptance-кода — разные экземпляры OfferError в TS-loader,
float с лишними знаками в тестовой цене, импорт scripts в opt-in pytest и ожидаемый
Windows ReadError при аварийном выходе — исправлены. Они не объявлены успешными
проверками приложения. Преднамеренный rollback возвращал 500 в изолированном
fault-процессе; это отдельная негативная проверка.

## Повторение

`alembic upgrade head`, production build и перезапуск API/frontend. Для нового
frontend на Vercel требуется обычный deploy этой сборки; состояние остаётся в
существующей PostgreSQL. Никакой второй БД или внешней realtime-подписки нет.

Из корня, через `.venv/Scripts/python.exe scripts/check_client_selection.py`:
`prepare → deploy → setup → http → processes → load → race → browser → lifecycle
→ restart-verify → verify → cleanup`.
`control` отдельно воспроизводит два старых model-only поиска на исходной factory.
Сначала сохранить результаты `http/processes/load`: lifecycle удаляет одно
тестовое предложение, browser намеренно завершает сессию второго менеджера.

Для постоянной PostgreSQL-регрессии перед cleanup задать
`CLIENT_SELECTION_LIVE_LEDGER` равным абсолютному пути
`.local/client-selection-ledger.json` и выполнить
`python -m pytest apps/api/tests/test_client_selection_postgres.py -m postgres -q`.
Без явной подготовленной disposable-сессии тест не обращается к рабочим данным.
Ledger нельзя печатать или коммитить; cleanup ограничен точными ID этого run.
