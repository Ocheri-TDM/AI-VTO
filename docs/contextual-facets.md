# Контекстные характеристики и фильтры категорий

> Материалы прежних приёмок перенесены в архив при очистке проекта.

14 ноября 2026. Реализовано на существующем PostgreSQL Research Index и HUD.
Локальная HTTP- и Edge-приёмка выполнена; Vercel не обновлялся, ngrok не запускался.

## Подтверждённые причины

В `ProductGridMixin.grid_response` список `effective_filters.options.sizes`
строился отдельным `DISTINCT` по всему `SupplierOffer.payload.metadata.size`.
Он не ограничивался подтверждёнными offer IDs текущего поиска. Это отдельный
список от уже рассчитанного `facets.size`: исправление только последнего не
убирало загрязнённые варианты из dropdown. Одно сырое `size` также смешивало
размер одежды, формат бумаги, вместимость и другие variation options.

На исходном запросе «Бутылки, кружки, зонты» было 106 глобальных вариантов
размера, а в фактической выдаче — 11 значений сырого размера, включая S/M/L/XL.
Проверка самих товаров установила второй дефект: шаблон `бутыл\w*`
распознавал **бутылочный зелёный** как товар «бутылка». Семь жилетов/курток
и один несессер попадали в выдачу. Исправлены формы существительного, включая
термобутылки; CSS/скрытие значений этот дефект не маскируют.

На одном сохранённом наборе из **1110 точных offer IDs** повторная локальная
проверка оставила **1102**. Все восемь исключённых вариантов с названиями,
исходной категорией и новым объяснением находятся в
membership-repair.json.
Исходные supplier payload не исправлялись задним числом.

Источники всех приведённых пользователем значений проверены SQL:

## Исполнение и типизация

`сохранённый intent → effective intent → SQL candidates → ProductPurpose/model
membership → snapshots веток → общий SQL scope выдачи/фасетов → DTO → HUD`.

`product_attributes.py` задаёт расширяемый реестр применимости, тип, единицу
и нормализацию. Поддержаны вместимость посуды в мл, размеры одежды, форматы
бумаги, диаметр/механизм зонта, мА·ч, ГБ, литры сумок/рюкзаков и диагональ
ноутбука. Поля без подтверждённых данных не создают пустые controls.

0,5 л / 0.5 l / 500 мл дают ключ `500` и подпись «500 мл».
Геометрия, вес, объём упаковки, SKU, цена и тираж не становятся вместимостью.
Явный атрибут варианта приоритетнее родительского; список всех размеров семьи
не наследуется каждым ребёнком. Неоднозначный явно заданный атрибут варианта
не заменяется нижестоящим предположением родителя. Для каждого значения
сохранены raw, поле и область происхождения. Неизвестное значение не равно нулю.

Миграция `0029_contextual_attributes` добавляет только производные
`offer_attribute_projections` и `offer_attribute_values`, с lookup index
`(attribute_id, value_key, offer_id)`. Версия проекции — `product-attributes-v4`.
Локальный backfill использует keyset-порции по 250, существующие упорядоченные
advisory locks offer IDs и отдельные короткие транзакции. Supplier HTTP не вызывается.
Заключительный пересчёт обновил 26 940 проекций; повторный запуск обработал **0**
строк и изменил **0** проекций. Новые поступления штатный ingest проецирует сам:
на следующем SQL-снимке было **27 053 / 27 053** проекций текущей версии.
Измеренный снимок не означает
полноты внешнего каталога.

`primary-product-v4` включает существующую совместимую revalidation сохранённых
research: сохраняет view/history, записывает прежние pools и пересчитывает
membership при открытии. Исходные intent, выбор и документы не очищаются.

## Scope и сохранение состояния

Дополнение 21 ноября 2026: общие условия после простого перечисления также
применяются ко всем его категориям. Запрос «Покажи мне Зонты ручки бутылки
черного цвета 100 шт» раньше оставлял цвет и тираж только у бутылок. Теперь
все три ветки получают BLACK и минимум 100, а HUD показывает общие значения.
Если внутри списка явно названы локальные условия («зонты, ручки и чёрные
бутылки»), они сохраняют свою область. Мягкие пожелания не превращаются в
обязательный цвет; строгие числовые границы сохраняются.

Проверено через основной HTTP API и PostgreSQL: 201 вариант — 38 зонтов,
110 ручек, 53 бутылки; SQL подтвердил BLACK и stock >= 100 у каждого.
В установленном Edge проверены общие поля и F5. Постоянные регрессии:
`apps/api/tests/test_trailing_list_scope.py`; связанные parser/grid/filter
проверки — 96 passed, compatibility — 68 passed, заключительные 18 новых
сценариев — passed. Это измеренная выборка, не постоянное число товаров.

`ResearchFilters.branch_attributes[stable_branch_id][attribute_id]` хранит
дополнительные характеристики. Сервер проверяет branch ID, допустимость поля
для понятия, тип, канонический ключ и лимиты значений; произвольный SQL-field
от клиента не принимается. Цвет, бренд, материал, цена и тираж остаются общими
в рамках существующих inherit/set/clear и условий исходных веток.

Фильтрация: `(бутылки AND 500 мл) OR (кружки AND 350 мл) OR зонты`.
Внутри одного многозначного условия — OR, между характеристиками ветки — AND.
Один offer в двух ветках учитывается один раз в общем matching_count.

SQL считает `COUNT(DISTINCT offer_id)` по полному проверенному pool до пагинации.
Для своего фасета снимается только соответствующее дополнительное ограничение;
соседние поля и исходные ограничения учитываются. Для допустимых альтернатив
ручного override используется отдельный snapshot подтверждённого контекста.
Поиск точной модели не расширяется до всей категории.

Скрытая ветка исключается из результатов и фасетов, сохраняя настройки.
Удалённая ветка отсутствует в текущем intent; восстановление возвращает её ID
и настройки. Активное значение с нулём остаётся видимым и снимаемым.
Reset возвращает исходные условия, а не весь каталог. Неподдерживаемое прежнее
условие явно показывается со снятием. Коллекция проекта от фильтров не меняется.

Общего кеша размеров нет. Context fingerprint включает intent/ветки/видимость,
ручные условия и применимую версию/дату проекции; sort/cursor его не меняют.
Расчёт фасетов выполняется в одном PostgreSQL read-only repeatable-read snapshot.
SQL-запросы агрегируют значения пакетно; запроса на каждый вариант dropdown нет.

## Интерфейс

В прежнем HUD появились подписанные группы характеристик категорий; одна
категория показывает своё поле непосредственно. Сохранены общие фильтры,
правая подборка, Current/Pulse и Geist. Категорийные chips содержат названия
и прежние действия. При новом запросе вместо прежних dropdown видна загрузка.
Используются существующие request generation/revision guards и общие dropdown.

Длинные списки показывают первые 60 значений, количество оставшихся и «Показать
ещё»; поиск охватывает все контекстные значения, выбранные закрепляются.
Скрытого постоянного top-N нет. Открытие dropdown не создаёт новый research fetch,
не запускает Qwen, VTO sync или дополнительный поиск.

Осмотр финальных снимков подтвердил исправление найденной при визуальной
проверке раскладки: типизированные группы занимают целую строку flex-HUD,
а не последний столбец с большой пустой областью.

Оригинальный `grid_response` из доверенного Git HEAD сравнивался с новым кодом
на **одном заново проверенном snapshot из 1216 offer IDs**, без записи research.
Три прогретых измерения, SQL counted через SQLAlchemy event, планы
`EXPLAIN (ANALYZE, BUFFERS)` сохранены без секретных параметров.

| Медиана всего grid_response | 979.08 ms | 670.56 ms |
| Фактические SQL statements | 6 | 9 |

Первая страница и matching_count совпали. Дополнительные запросы — пакетные
контекстные агрегации и версия проекции, а не N+1. Планы показали применение
`ix_offer_attributes_lookup` и существующих PK. В timings прежняя неточная
константа `sql_queries` заменена явным `facet_sql_queries`; полное число SQL
выше измерено независимо. Это небольшой замер, не нагрузочный p95 или обещание
такого ускорения для любой категории. Результаты и планы:

## Сохранность, воспроизведение и границы

Перед очисткой fingerprints совпали для исходных **3 users, 4 projects,
68 messages, 26 collection items, 17 documents, 22 revisions, 4 shares**;
сохранены 309 файлов документов и encryption key. Все **25 746 исходных
offer identities** остались на месте. На проверке было 27 313 offers вследствие
штатного фонового импорта. Коммерческие observations, SKU, изображения и цены
backfill не записывает; общий fingerprint каталога при продолжающемся импорте
не объявляется неизменным. Политика stock, worker limits, scheduler, публичные
предложения, клиентские отметки, уведомления и Logout кодом задачи не менялись.
Проверка исходных данных.

Обновление: штатный `alembic upgrade head`, затем
`.venv/Scripts/python.exe scripts/backfill_product_attributes.py`, restart API
и build/restart frontend. Backfill возобновляется по версии/наличию проекции;
`--limit` ограничивает запуск, `--verify-all` проверяет также source hashes.

Acceptance: `scripts/check_contextual_facets.py prepare` → `before` на исходном
коде → обновление → `after` → `accept` → `benchmark` → `browser` → `verify` →
`cleanup`. PostgreSQL regression запускается с `CONTEXTUAL_FACETS_POSTGRES=1`
и `pytest ...test_contextual_facets_postgres.py -m postgres`; его DDL ограничен
собственной временной схемой. Оригинальная схема не пересоздаётся.

Неопубликованные/неоднозначные свойства остаются неизвестными. Поддержан
конечный расширяемый реестр свойств, а не автоматическая онтология всех
атрибутов VTO. Сырой вариант без подтверждённого размера может быть товаром
выдачи без опции соответствующего фильтра. Новые товары становятся доступными
при новом поиске по прежнему контракту snapshot; сохранённый поиск автоматически
не расширяется всем поступившим каталогом.

Очистка выполнена: удалены по проверенным ID один disposable пользователь и
восемь его проектов; пользовательских документов у него не создавалось.
Отдельный Edge profile, debugging listener и secret ledger закрыты/удалены.
В cleanup.json подтверждены прежние
fingerprints, 25 746 исходных offer identities, 309 файлов и ключ. На этой
проверке каталог содержал 27 523 offers. API, frontend и proxy вернули HTTP 200.
PostgreSQL, Ollama, API и frontend работают; ngrok выключен. Постоянные тесты,
migration, производные проекции и доказательства сохранены.
