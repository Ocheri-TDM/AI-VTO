### Сортировка и оттенки

Для цены использованы числовые значения `ProductObservation.price_kzt`.
Неизвестные цены идут последними в обоих направлениях, равные цены — по ID;
это прежнее правило ties/null единой сетки. Числовой ноль в каталоге не
подменён неизвестной ценой. На независимой фикстуре самый дешёвый товар
изначально за первой страницей; обе сортировки сохраняют полный набор ID,
включая неизвестную цену и равные цены, без повторов при догрузке.

Navy — отдельное строгое значение `NAVY`, DARK_BLUE — `DARK_BLUE`. Правило
существовало в регрессиях grid; поисковое совпадение legacy ColorNormalizer
не является основанием объединять их. Выбор других оттенков остаётся явным.

Из 104 красных ручек исключены по сырому цвету только следующие предложения:
`vto:1281645`, `vto:1281668`, `vto:1282290`, `vto:1292989`, `vto:1818053`,
`vto:1944541`, `vto:1948572`, `vto:1953282`. Опубликованные метки: «Бордовый»,
«бордовый матовый/серебристый», «бордовый/серебристый», «бордовый/золотистый»,
«матовая бордовая». Цветовая нормализация и сами фотографии/данные VTO не
переписаны. Если поставщик указал только «красный» без оттенка, более точное
различие невозможно — это явно сообщается в выдаче.

## Отправка, история и восстановление

Два дефекта подтверждены по исходному коду: `api.failure` показывал сообщение
про API_BASE_URL для любого 503, а `AuthGate` считал любой отказ `/auth/me`
завершением сессии. Это причины неправильного объяснения отказа, но не
доказательство причины единичного инцидента на Vercel.

- `lib/api.ts` разделяет transport error, 401, 502/503/504, invalid response и
  явный `BACKEND_NOT_CONFIGURED`. Последний возвращается отдельным route
  только для сборки без backend origin.
- `AuthGate` переходит на вход по подтверждённому 401; временный отказ чтения
  сессии оставляет экран подключения с повтором.
- Перед отправкой сохраняются точный текст, UUID запроса, время и при первом
  чате UUID создания в sessionStorage, изолированно по пользователю и чату.
  Подтверждённый сервером чат получает draft до последующего чтения проектов.
  Только совпавший UUID очищает draft. Создание и повтор POST используют
  прежний механизм идемпотентности.
- Новый GET `/api/projects/{project}/requests/{request}` читает сохранённый
  `ConversationTurn` строго для владельца, возвращает статус и признак
  актуальности epoch. Внешнему клиенту не передаются внутренние ошибки SQL.
  При потере ответа выполняется чтение, а не автоматическая повторная
  отправка. После подтверждения история/активная выдача синхронизируются.
- Перед применением успешного POST проверяется актуальный receipt: ответ,
  задержанный сетью или другой вкладкой, не подменяет более позднюю выдачу.
  `useResearch`, `useConversation` повторяют чтение при восстановлении связи;
  `requestGeneration` защищает переключение проектов/поисков.

UTC+5: шесть GET auth/requests со статусом 200, один `/api/auth/me` со статусом

locator находил также Next route announcer; уточнён locator к карточке входа,
а не поведение приложения.
