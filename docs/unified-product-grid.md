# Unified product grid — 2026-10-30

Последующая проверка основного назначения и новый HUD описаны в
[product-purpose-hud.md](product-purpose-hud.md). Числа ниже относятся к
предыдущему снимку до этой доработки.

Новые запросы возвращают `mode=GRID` и один `ResearchSession`. Автоматическая
сборка, количество наборов, обязательные слоты и альтернативы внутри кейсов
выведены из рабочего пути. Ниже — результаты этой задачи; предыдущие отчёты
об Assembly описывают прежнее поведение.

## Изменения и причины

Раньше `/projects/{id}/requests` выбирал между Research и HardRequestService.
Многокатегорийный запрос запускал allocator, recovery и отдельный Case View.
Обычный Research гидратировал полный пул Product, затем фильтровал его в памяти.
Старые frontend hooks поддерживали конкурирующие активные состояния.

Теперь ProjectQueryService использует прежние проекты, ProjectQuery,
ResearchSession, ResearchView, историю и PostgreSQL advisory locks. ProductGridMixin
расширяет существующий IndexedResearchService; другого каталога или поисковой
базы нет. Общий семантический parser и позиционные ограничения переиспользованы.

Удалены публичный assembly router, frontend HardRequest DTO/API, Case View,
rebuild/select-candidate/SSE hooks сборки. HardRequestService не создаётся в
`create_app`, не восстанавливает jobs и не получает публикации индекса. Старый
backend compatibility-код оставлен для архивных форматов и регрессионных тестов,
он не зарегистрирован в приложении. Прежние POST assembly endpoints отвечают
410. Таблицы и исторические записи не удалены. Незавершённые сборки получают
ARCHIVED при восстановлении приложения; VTO jobs это не затрагивает.

Формулировка «Собери 10 наборов из ручек и кружек» выделяет категории, показывает
пояснение об отмене автоматической сборки и возвращает товары. Число 10 не
становится ни тиражом, ни LIMIT, ни числом карточек.

## План, фильтры и порядок

`ResearchIntent.branches` хранит упорядоченные категории, локальные цвета,
количества, материалы и цены. Глобальные условия наследуются при построении
веток; локальные имеют приоритет. SQL выбирает объединение веток, а не их
пересечение. Отсутствующая ветка не обнуляет остальные.

SupplierOffer ID встречается один раз, в первой подходящей ветке; DTO сохраняет
`matched_categories` для остальных соответствий. Разные VTO variation IDs
остаются разными карточками. Порядок внутри категории определяется сортировкой,
предпочтениями и стабильным ID; квот на категорию нет.

Исходное сообщение не переписывается ручными фильтрами. Дополнительные условия
живут в `ResearchView.filters`, сортировка и selections — в том же view. Reset
снимает дополнительные фильтры, сохраняя исходные требования и selections.
Явная замена/снятие исходного условия проходит через ревизию intent. Undo
восстанавливает соответствующий снимок intent/view и повышает version.

Фильтры панели: несколько брендов через OR, цвет, материал, размер, диапазон
цен и минимальное опубликованное количество; измерения соединяются AND.
Бренд берётся из сохранённых данных VTO, регистр и пробелы нормализуются,
исходное написание остаётся в facets. Неуказанный бренд — отдельное значение.
Список брендов относится к полному базовому результату с учётом остальных
фильтров; собственное измерение исключается при подсчёте своего facet.

SQL применяет фильтры. Facets считаются линейно по скалярной проекции полного
пула, без гидратации Product DTO. HUD показывает локальные и глобальные
условия, дополнительные фильтры, исключения и предпочтения. Происхождение
дополнительных условий хранится как manual/chat и показывается tooltip.

Уточнения бренда, цены, материала и сортировки не вызывают Qwen, supplier HTTP
или jobs импорта. Добавление/удаление категории и локальная смена цвета
используют тот же ResearchSession и стек ревизий. Самостоятельный поиск
создаёт новую запись и новый selection state.

## Исправления точности

«Термокружка с ручкой» не принимается за пишущую ручку. Проверка учитывает
назначение; явно названная шариковая ручка или гибрид с вечным карандашом
сохраняют многофункциональность. Регрессии покрывают отрицательный пример и
появление гибрида в первой подходящей ветке без дублирования.

Live-проверка выявила и исправила ещё одну ошибку: Query Understanding заменял
слова в «подарки для сотрудников в дороге» популярными словами каталога.
Проверенный исходный список категорий и фразы назначения/аудитории теперь
защищены от такого переписывания. Без защиты было 0 результатов по ошибочно
сформированной динамической фразе; после — 528 вариантов по существующему
discovery-плану с ценой до 7000 ₸. Это проверка интерпретации и ограничений,
не экспертная оценка релевантности каждого подарка.

Открытые категории могут подтверждаться названием и категорией/breadcrumbs
поставщика. Они не ограничены списком канонических seed-категорий.

## Пагинация и сохранение

Backend сохраняет полный пул ID и соответствия веткам. HTTP отдаёт максимум
100 полных карточек; дополнительно гидратируются только явно выбранные товары.
SQL для больших списков PostgreSQL использует typed arrays, избегая лимита
числа bind-параметров. Парные сравнения моделей отсутствуют.

Счётчики разделены на `base_total`, `filtered_total`, число загруженных карточек,
`selected_count` и `hidden_selected_count`. Скрытие фильтром не снимает selection.
Выбранные товары можно открыть и снять выбор.

Cursor связан с research ID, revision, view version и упорядоченным списком ID.
Старый cursor получает 409. Новый импорт не добавляет карточки между страницами
этого снимка: новые варианты доступны новому поиску/явному обновлению индекса.
Изменение существующего остатка или цены пересчитывает условия; новое нулевое
наблюдение не остаётся подходящим для исходного требования 300 шт.

Project lock защищает смену активного запроса, research lock и version —
изменения view между процессами. Frontend проверяет generation, ID и revision,
включая запоздалый ответ сохранения selections. Старый SSE не переключает проект
или активный запрос. F5 читает active ProjectQuery, а не последнюю по времени
историческую запись.

История кейсов доступна как архив с явным повторением в товарном поиске.
При открытии старого обычного исследования совместимое JSON-состояние переводится
в unified на том же ResearchSession ID: действующие условия, selections и
история остаются, известные старые brand/material/size filters переносятся в
новые поля. Повторного обхода VTO для этого нет.

SQL измерен SQLAlchemy event-счётчиком в отдельном временном API с выключенным
scheduler на **той же PostgreSQL**. Он включает auth, ownership, блокировки и
persistence. В самом view четыре запроса: скалярный базовый пул, фильтрованный
пул, карточки страницы/selections и их availability. Нельзя выдавать эти четыре
за полное число запросов initial search.

Байты без `*` — длина фактического HTTP body. Для двух PATCH-операций со `*`
сохранена длина повторно сериализованного JSON с экранированием Unicode,
поэтому это диагностический размер, а не точный wire size.

До изменения тот же запрос четырёх категорий вернул COMPOSITE за 0,530 с,
22 089 байт; сборка дошла до COMPLETED_FULL. Это был ответ плана сборки,
не страница товаров: напрямую сравнивать его размер/latency с GRID нельзя.
Количество прежних гидратированных объектов и SQL для этого baseline не измерено.

После включения нового основного API на 8000 повторная проверка дала GRID:
509 вариантов, первая страница 100; бренд Molti — 4, сочетание фильтров — 1.
Три независимых пользователя получили HTTP 202; попытки читать чужой проект —
404. В инструментированном прогоне времена были 0,381 / 0,350 / 0,553 с.
Это ограниченный smoke-тест, не нагрузочный p95.

## Сохранность и ограничения

Reset, миграции, удаление таблиц, каталога или пользовательских данных в этой
задаче не выполнялись. Исходные VTO adapter, HTTP client, traversal, ingest и
checkpoints не переписывались. Резервный dump предыдущего перехода сохранён.

При включении нового основного API у существующего VTO job был свободен lease;
job уже ожидал retry после VTO_HTTP_ERROR. Его ID
`3af11531-88ce-4c5f-b33d-869c4045d606`, page=22, processed=1573 и очередь
сохранены. Второй VTO crawler не запускался. HTTP-ошибка источника и полнота
импорта не исправляются и не объявляются PASS в задаче удаления Case.

Новый поиск использует доступный индекс. Незнакомые назначения и неоднозначные
слова ограничены существующим resolver/discovery; этот этап не является новой
оценкой полноты семантического поиска. Не все варианты обязаны иметь известный
бренд, материал, размер или числовой остаток. Нулевой/неизвестный остаток не
превращается в положительное количество. LAST_KNOWN_STOCK_ALLOWED сохранён;
цвета и размеры не суммируются для тиража.

Временные измерительные процессы/JSON/logs удаляются после записи результатов.
Постоянные проверки: `scripts/check_product_grid.py`, обновлённый
`scripts/check_vto.py`, backend integration tests и `npm --prefix apps/web test`.
Все созданные HTTP-тестами проекты и аккаунты удаляются по точным записанным ID.
