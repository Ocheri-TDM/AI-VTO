# TASK — MULTI-USER CONCURRENCY & PERFORMANCE HARDENING
## Souvenir Studio — Production-Oriented Stability for 10 Concurrent Users

**Role:** Senior Backend Engineer / Python AsyncIO Architect / PostgreSQL Performance Engineer / SRE / QA Automation Engineer.

**Repository:** `Ocheri-TDM/AI-VTO`

**Task type:** Investigation + Root Cause Analysis + Targeted Implementation + Regression Testing + Real Load Testing.

**Priority:** P0/P1.

**Important:** This is an implementation task, not another read-only audit or architectural planning stage.

---

# 1. MAIN OBJECTIVE

Make Souvenir Studio reliable and responsive when **5–10 real users simultaneously work with different projects, execute SIMPLE searches, create COMPOSITE requests, refine searches, rebuild cases, navigate history and receive SSE updates**.

The application must preserve:

- Correct user and project isolation.
- Correct active workspace and query revisions.
- Correct SIMPLE ↔ COMPOSITE transitions.
- Correct search results and product identities.
- Stable background catalog indexing.
- Stable PostgreSQL transactions.
- Stable SSE behavior.
- Predictable response latency.
- No accidental deletion or modification of existing production data.

Do not solve performance problems by reducing search recall, hiding products, skipping suppliers, disabling business rules or weakening availability checks.

The objective is to optimize execution, not reduce correctness.

# 4. P0 — REPRODUCE AND FIX THE HTTP 503

A confirmed failure occurred during this same-project sequence:

1. SIMPLE: `термокружка`
2. REFINE: `оставь черные`
3. SIMPLE: `ежедневник`
4. COMPOSITE: `Собери 5 наборов из термокружек, ручек и ежедневников`
5. SIMPLE: `покажи только термокружки`

The final operation returned HTTP 503.

The failure was classified as a SQLAlchemy/database exception, but the exact SQLSTATE and traceback were not preserved.

## Required investigation

Trace:

`HTTP request → authentication → project ownership → query router → active intent → workspace transition → transaction → archive old query → activate new query → commit → response`

Inspect:

- Transaction boundaries.
- Session lifecycle.
- SQLAlchemy exceptions.
- Advisory lock acquisition/release.
- In-process project locks.
- Nested transactions.
- Active query uniqueness constraints.
- Concurrent revisions.
- Database connection checkout.
- Pool timeout.
- Transaction rollback.
- Foreign-key relationships.
- Archiving previous SIMPLE/COMPOSITE revisions.

Determine whether the failure originates from:

- Deadlock.
- Connection exhaustion.
- Invalid transaction state.
- Stale session.
- Constraint violation.
- Concurrent modification.
- Incorrect lock lifetime.
- Incorrect transaction ordering.
- Another demonstrated cause.

Do not choose a cause without evidence.

## Required fix

Make the transition atomic.

The operation must not leave the project in a partially switched state.

The server must preserve a consistent active workspace after success, rollback or retry.

Use existing transaction and locking mechanisms where possible.

Do not introduce unnecessary distributed infrastructure.

If a retry is appropriate, retry only known transient database errors and only where idempotency and transaction safety are guaranteed.

Do not hide the problem behind generic retries.

## Acceptance

Repeat the exact sequence multiple times.

Then repeat it while other users execute SIMPLE and COMPOSITE searches.

Required:

- No HTTP 500/503.
- No orphan active query.
- No two active workspaces.
- No incorrect query title.
- No loss of chat history.
- No cross-user state contamination.
- Correct active query after F5.

# 7. P1 — DETERMINE THE ACTUAL BOTTLENECK

Reproduce the baseline under controlled conditions.

Use the same database, comparable background workload and identical query mix for before/after measurements.

Profile the execution path.

Investigate the following hypotheses independently.

## Hypothesis A — Event-loop blocking

Check for:

- Synchronous CPU-heavy ranking.
- Large Python loops.
- Synchronous database or filesystem operations.
- JSON serialization.
- Blocking calls inside async endpoints.
- Playwright work competing with API traffic.

Identify functions responsible for measurable event-loop lag.

## Hypothesis B — PostgreSQL

Inspect:

- Pool checkout wait.
- Connection hold duration.
- Slow queries.
- Missing indexes.
- Expensive joins.
- Large intermediate result sets.
- Repeated hydration.
- Unnecessary transactions.
- Advisory lock contention.
- N+1 queries.

Use `EXPLAIN (ANALYZE, BUFFERS)` on representative read-only queries where safe.

Do not add indexes without validating query plans.

## Hypothesis C — Python-side materialization

Determine whether search unnecessarily:

- Loads the full product pool into Python.
- Repeatedly normalizes the same attributes.
- Rebuilds facets for every request.
- Reconstructs unchanged product DTOs.
- Performs expensive grouping/deduplication.
- Serializes thousands of objects to return 100 cards.

## Hypothesis D — Background worker contention

Measure whether supplier crawling competes with interactive API requests for:

- CPU.
- PostgreSQL connections.
- Event-loop scheduling.
- Browser resources.
- Memory.

## Hypothesis E — LLM contention

Check whether concurrent semantic requests are bounded and whether HTTP connections are reused.

Do not assume Ollama is responsible for deterministic SIMPLE latency.

For each hypothesis, record:

- Evidence.
- Measured contribution.
- Root cause or rejection.
- Proposed correction.
- Expected impact.

# 8. P1 — OPTIMIZE SIMPLE SEARCH

The application uses a persistent global Research Index.

Normal SIMPLE searches must not require supplier browsing.

Optimize the existing retrieval pipeline while preserving the complete matching product pool.

Important distinction:

- Full matching pool must remain logically available.
- The initial HTTP response does not need to hydrate every matching product.
- UI pagination must not truncate the underlying research result set.

Investigate SQL-first retrieval, efficient membership representation, incremental pagination and reusable normalized attributes.

Where appropriate:

- Push filtering into PostgreSQL.
- Avoid repeated full-pool hydration.
- Reduce duplicate SQL queries.
- Avoid rebuilding unchanged search documents.
- Cache safe immutable catalog metadata.
- Keep session-specific filters and selections isolated.
- Use bounded pagination.
- Optimize facets with database aggregation when beneficial.
- Reuse expensive derived data only when cache invalidation is correct.

Never replace full recall with arbitrary `LIMIT 100` or `LIMIT 180`.

Do not change ranking semantics solely to improve latency.

Verify that optimized results have the same IDs and applicable ordering as the baseline.

# 11. P1 — API AND BACKGROUND WORKER ISOLATION

The current deployment has one Uvicorn worker with background scheduling in the same process.

Investigate whether this is contributing to interactive latency.

Do not immediately change Uvicorn to `workers=4`.

The application contains process-local state:

- In-memory locks.
- Intent caches.
- Active task dictionaries.
- Background scheduler ownership.
- Browser/Playwright resources.

Launching multiple processes without coordinating these systems could duplicate jobs or produce inconsistent behavior.

Evaluate two approaches.

## Option A — Optimize the existing single-process architecture

Use this if measurements show it can satisfy the target safely.

## Option B — Separate API execution from background workers

Use this if contention is demonstrated and separation is necessary.

Possible architecture:

`Next.js → FastAPI API process → PostgreSQL`

`Independent background worker process → PostgreSQL → supplier crawlers`

`Ollama → bounded inference execution`

If implementing separation:

- Keep durable jobs in PostgreSQL.
- Ensure one logical scheduler owner.
- Prevent duplicate leases.
- Preserve checkpoints.
- Support graceful shutdown.
- Support restart recovery.
- Avoid breaking local Windows development.
- Document Ubuntu deployment.

Choose the smallest safe architecture that meets the measured requirements.
